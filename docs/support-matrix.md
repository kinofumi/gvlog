## エンコード設定の診断結果（2026-10-08）

アプリ内の「エンコードテスト（診断）」で、コーデック文字列 × latencyMode の各組み合わせを
1080x1920 / 30fps で実際に 5 フレームエンコードした結果。「判定」は `canEncodeVideo`、「実際」は実エンコードの成否。

| 端末 | 結果 |
| --- | --- |
| iPhone、iOS 18.7 / Safari 27.0 | 10 通りすべて 判定 可 / 実際 成功（`avc1.42E028`、`avc1.42002A`、`avc1.4D4028`、`avc1.640028`、自動 × `quality`、`realtime`）。1 件あたり 110〜170ms |
| macOS、Headless Chrome 151 | 10 通りすべて 判定 可 / 実際 成功 |
| Android 10、Chrome 154 | 10 通りすべて 判定 可 / 実際 成功。初回の `avc1.42E028` / `quality` だけ 1052ms（エンコーダの初期化）、以降は 350〜500ms |

### iPhone で最初に失敗した原因（推定）

- 最初の版は候補の先頭が `avc1.42E01F`（Constrained Baseline、Level 3.1）で、`canEncodeVideo` が可と答えた候補をそのまま使っていた。
- Level 3.1 の上限は 1280x720 相当で、1080x1920 は超えている。Headless Chrome は判定の段階で不可と答えたが、
  iOS Safari は判定で可と答え、実エンコードで「Encoding task failed」（WebKit 内部のエラー文）を出したと考えられる。
- 対策として、候補から Level 3.1 を外し、各候補を実際に数フレームエンコードして成功したものを使う方式に変えた。
  `latencyMode: 'quality'` が Safari で止まる既知の不具合（mediabunny issue #541）は、この端末では再現しなかった。

### Android で出た「TypeError: network error」（2026-10-09）

- 書き出しの途中で `TypeError: network error（avc1.42E028 / quality）` が表示された試行がある。エンコード設定は診断で成功しているものなので、エンコーダの失敗ではない。
- Chrome では `Blob.arrayBuffer()` がファイルを読めなかったときにこの文言の TypeError を出す。アプリで書き出し中にファイルを読むのは
  動画だけ（`BlobSource` が必要な範囲を少しずつ読む）なので、選択した動画ファイルが書き出し時点で読めなくなっていたと考えられる。
- Android ではファイル選択で渡される File が一時的なアクセス権に基づくことがあり、アプリ切り替えや時間経過で読めなくなる場合がある。
  同じ端末で別の試行は成功しているので、端末固有の恒常的な問題ではない。
- 対応: 取り込み時に動画をまるごとメモリへ読み込む（ADR 012）。2026-10-13 に同じ Android で書き出しと保存を再確認し、再発なし。

## 確認のしかた

1. PC で `npm run dev` を起動し、同じ Wi-Fi のスマホから `https://<PC の IP>:5173/groupe-vlog/` を開く
   （自己署名証明書の警告が出るので「詳細」→「このまま開く」）。
2. 名前とスポットを入れ、写真 1 枚と動画 1 本を選び「書き出す」。
3. 完了したら「共有（写真に保存）」→ 写真アプリで再生。
4. 出力ファイルを PC に送り、`scripts/verify-output.sh <ファイル>` で属性と冒頭・中央・末尾のフレームを確認。
5. CapCut に読み込んでタイムラインに置けることを確認。
6. この表に OS バージョン、機種、結果を追記する。
