先に知っておくとよい、Python との大きな違い

  • 数は 1 種類。 number に int と float の区別がない。7 / 2 は 3.5。整数にしたいときは Math.floor を自分で呼ぶ（このアプリはフレーム番号を整数で持つので、至るところで呼んでいる。ADR 008）。
  • 「無い」が 2 つある。 undefined（未設定）と null（意図して空）。このアプリでは、省略できるフィールドは undefined、「選んでいない」は null と使い分けている。
  • const は再代入禁止であって、不変ではない。 const items = [] でも items.push(x) はできる。不変にしたいなら、変えずに新しい値を作る（4 章）。
  • 型は実行時に消える。 型チェックは tsc がビルド前にやるだけ。実行中には型情報は無い。外から来た値（JSON、ファイル）は unknown として受けて自分で確かめる（2 章の validatePreset）。
  • インデントではなく波括弧。 セミコロンはこのリポジトリでは付けない（prettier の設定）。

第 2 章 型を読む

題材: src/model/types.ts、src/model/validate.ts 目標: types.ts の型を Python の dataclass と Literal に置き換えて説明できる。validatePreset がなぜ unknown を受けるか言える。

型エイリアスは dataclass に近い

export type GroupPreset = {
  id: string
  name: string
  aspect: '16:9' | '9:16'
  width: number
  height: number
  fps: 30
  maxFrames: number
}

Python で書くなら:

@dataclass
class GroupPreset:
    id: str
    name: str
    aspect: Literal['16:9', '9:16']
    width: float
    height: float
    fps: Literal[30]
    max_frames: float

違いが 3 つある。

  1. クラスではない。 type は「この形のオブジェクト」という名前を付けるだけで、コンストラクタもメソッドも無い。作るときは { id: 'default', name: 'Vlog', ... } と書く（src/model/defaults.ts）。
  2. number は float。 width: number に 1080.5 も入る。整数であることは型では言えないので、Number.isInteger で実行時に確かめる（validate.ts）。
  3. フィールド名は camelCase。 maxFrames。Python の snake_case とは違う。

リテラル型と union

aspect: '16:9' | '9:16'
fps: 30

| は「どちらか」。Python の Literal['16:9', '9:16'] と同じ。fps: 30 は「30 という値しか入らない」型。v1 では fps を固定している（ADR 009）ので、型で縛っている。

export type Transition = {
  type: 'cut' | 'crossfade' | 'fadeWhite'
  durationFrames: number
}

Python なら Enum を作るところだが、TypeScript では文字列リテラルの union で済ませることが多い。値がそのまま文字列なので、JSON に保存しても読み戻しても変わらない。

? は「無くてもよい」

export type TimelineItem = {
  itemId: string
  durationFrames: number
  transitionOut?: Transition
  caption?: CaptionTiming
}

transitionOut? は「無いかもしれない」。無いときの値は undefined。Python の Optional[Transition] = None に近いが、2 点違う。

  • 無いときは None ではなく undefined。
  • フィールド自体が 存在しなくてもよい。{ itemId: 'a', durationFrames: 150 } はこの型を満たす。

使う側は if (item.transitionOut) で確かめてから触る。item.transitionOut.type と無確認で書くと型エラーになる（'item.transitionOut' is possibly 'undefined'）。

& で型を合体する

export type Caption = CaptionTiming & {
  text: string
  presetId: 'band' | 'outline' | 'box'
  ...
}

& は「両方のフィールドを持つ」。Python の継承（class Caption(CaptionTiming)）に近いが、親子関係は無く、単にフィールドが足し合わさる。

kind で見分ける union（このアプリで一番大事な型）

export type PhotoItem = ItemBase & { kind: 'photo'; kenBurns: KenBurns }
export type VideoItem = ItemBase & {
  kind: 'video'
  sourceDurationFrames: number
  trimStartFrames: number
}
export type MediaItem = PhotoItem | VideoItem

MediaItem は写真か動画のどちらか。どちらかは kind を見れば分かる。TypeScript は if で kind を調べると、その中では型を絞り込む。

// src/timeline/trim.ts
if (item.kind !== 'video') return item
// ここから下では item は VideoItem。trimStartFrames に触れる
const trimStartFrames = clampTrimStart(
  item.trimStartFrames,
  item.sourceDurationFrames,
  visibleLength,
)

Python 3.10 の match item: case VideoItem(): ... に相当する。isinstance の代わりにフィールドの値で見分ける、と覚える。

構造的な型: 「形が合えば通る」

types.ts のコメントにこうある。

MediaItem はこの型（TimelineItem）を含むので、そのまま渡せる。

compileTimeline(items: TimelineItem[]) に MediaItem[] を渡せるのは、MediaItem が TimelineItem の全フィールドを持っているから。継承の宣言は要らない。Python の Protocol（静的なダックタイピング）と同じ考え方。

この性質を使って、src/timeline/ の関数は 必要な最小限のフィールドだけを持つ型 を受ける。テストでは { itemId: 'a', durationFrames: 40 } のような小さいオブジェクトを渡せばよく、写真の寸法やファイル名を書く必要がない（clamp.test.ts を見る）。

unknown と as: 外から来た値

export function validatePreset(value: unknown): ValidationResult {
  if (typeof value !== 'object' || value === null) {
    return { ok: false, errors: ['プリセットの形式が不正です。'] }
  }
  const p = value as Record<string, unknown>
  • unknown は「何が来るか分からない」。Python の Any と違い、確かめるまで何もできない。value.id と書くと型エラー。
  • typeof value !== 'object' で絞り込んでから、as Record<string, unknown> で「文字列キーの辞書として扱う」と宣言する。Record<K, V> は Python の dict[K, V]。
  • 各フィールドを typeof p.id !== 'string' のように 1 つずつ確かめ、最後にそろった値で GroupPreset を組み立てる。

as は「私が責任を持つのでこの型として扱って」という宣言で、実行時には何もしない。確かめた直後にだけ使う。確かめずに as で黙らせるのは、Python で # type: ignore を貼るのと同じ。

戻り値の型も union になっている。

export type ValidationResult = { ok: true; preset: GroupPreset } | { ok: false; errors: string[] }

ok が true なら preset がある、false なら errors がある。呼ぶ側は if (result.ok) で分岐すれば、それぞれの中で正しいフィールドだけが見える。例外を投げずに結果を型で返す書き方で、Python の Result 型を自作するのに似ている。

as const

const SIZE_BY_ASPECT = {
  '16:9': { width: 1920, height: 1080 },
  '9:16': { width: 1080, height: 1920 },
} as const

as const を付けると、width の型が number ではなく 1920 という値そのものになり、キーも '16:9' | '9:16' に固定される。これで SIZE_BY_ASPECT[aspect] が「aspect はこの 2 つのどちらか」と確かめたあとだけ通る。

import type

import type { GroupPreset } from './types'

型だけを読み込むときは import type。型は実行時に消えるので、このファイルからの依存も消える。値（関数や定数）を読み込むときは普通の import。

?? と || は違う

?? は左が null か undefined のときだけ右を使う。Python の or に近い || もあるが、|| は 0 や '' でも右を使ってしまう。フレーム数のように 0 が意味を持つ値には ?? を使う。

変数

const errors: string[] = []
let cursor = 0
  • const: 再代入しない。ほぼこれだけ使う。 ただし中身（配列の要素、オブジェクトのフィールド）は変えられる。errors.push(...) は通る。
  • let: 再代入する。ループのカウンタや累積に使う。
  • var: 使わない（古い書き方）。

型は多くの場合書かなくてよい。let cursor = 0 で number と推論される。const errors: string[] = [] に型を書いているのは、空の配列からは要素の型が分からないため。

number の罠

Python 中級者が最初にはまる場所。

  • 7 / 2 は 3.5。整数除算が無い。

ブラウザは 1 本のスレッド

JavaScript は基本的に 1 本のスレッドで動き、待ち時間（ファイル読み込み、動画のデコード、タイマー）はイベントループに任せる。Python の asyncio と同じモデル。違いは、最初から全部が非同期 であること。同期で待つ手段（time.sleep）が無い。

async function は呼ぶと必ず Promise を返す。await は Promise が終わるまで、その関数の続きを後回しにする。Python と同じ。

new Promise で手作りする

withTimeout.ts は async ではなく new Promise で書いてある。

export function withTimeout<T>(promise: Promise<T>, ms: number, signal?: AbortSignal): Promise<T> {
  return new Promise((resolve, reject) => {
    ...
  })
}

new Promise((resolve, reject) => { ... }) は「結果を後で入れる箱」を作る。resolve(v) を呼ぶと成功、reject(e) で失敗。箱の中で 3 つの出口を待っている。

  1. 元の promise が終わる → その結果をそのまま流す。
  2. ms ミリ秒たつ → タイムアウトのエラー。
  3. signal が中断される → 「中断されました」のエラー。
promise.then(
  (value) => finish(() => resolve(value)),
  (error) => finish(() => reject(error)),
)

.then(成功時, 失敗時) は await を使わない書き方。async にすると「元の promise が失敗したあともタイマーを片付ける」が書きにくいので、ここでは .then を選んでいる。

「1 回だけ終わる」を守る

let settled = false
function finish(settle: () => void) {
  if (settled) return
  settled = true
  clearTimeout(timer)
  signal?.removeEventListener('abort', onAbort)
  settle()
}

3 つの出口のどれが先に来ても、finish を通して 1 回だけ 結果を入れ、タイマーとイベントの登録を片付ける。Promise は 2 回目の resolve を黙って無視するが、タイマーの片付けは自分でやらないと残る。

Python で asyncio.wait_for を自作するときの done フラグと同じ。

AbortSignal: 協力的な中断

if (signal?.aborted) {
  onAbort()
} else {
  signal?.addEventListener('abort', onAbort)
}

AbortController を作った側が controller.abort() を呼ぶと、signal に 'abort' イベントが飛ぶ。受ける側はそれを聞いて自分で止まる。Python の task.cancel() が CancelledError を投げ込むのに対し、こちらは「お願い」なので、聞いていない処理は止まらない。

「すでに中断済みの signal を渡されたら、イベントは来ない」ので先に aborted を見る。テストの最後の it がこの場合を確かめている。

考え方: CSS をクラス名で書く

Tailwind では、CSS を別ファイルに書く代わりに、1 つの CSS プロパティ = 1 つのクラス を要素に並べる。

<p class="rounded border border-red-300 bg-red-50 px-3 py-2 text-sm text-red-700"></p>

は、ふつうの CSS で書くと:

border-radius: 0.25rem;
border-width: 1px;
border-color: (赤の薄い色);
background-color: (赤のごく薄い色);
padding-left: 0.75rem;
padding-right: 0.75rem;
padding-top: 0.5rem;
padding-bottom: 0.5rem;
font-size: 0.875rem;
color: (赤の濃い色);

利点は、要素とその見た目が同じ場所にあること。欠点は、クラスの名前と数の規則を覚えるまで読めないこと。この章はその規則を、このアプリにあるクラスだけで覚える。

数の規則: 1 = 0.25rem = 4px

p-2、gap-3、mb-12、w-12、min-h-11 の数字はすべて同じ目盛り。4 倍すると px になる。

第 8 章 状態とデータの流れ

題材: src/state/store.ts、src/state/projectActions.ts とそのテスト、src/components/MediaList.tsx 目標: スライダーを動かしたときに、どのファイルのどの関数を通って画面が変わるかを追える。

全体像

[部品]  FrameSlider の onChange
  ↓ setItemDuration(itemId, frames)
[store] useAppStore の setItemDuration
  ↓ actions.setItemDuration(project, itemId, frames)
[純粋関数] projectActions.ts → timeline/durations.ts、clamp.ts、trim.ts
  ↓ 新しい project
[store] set({ project })
  ↓ 変わった部分を見ている部品だけが再描画
[部品]  MediaList、TotalDuration、PreviewCanvas …

考え方は Python でも書ける。「状態は 1 つの dict。変更は new = f(old, ...) を返す純粋関数。dict を差し替えたら、購読している関数を呼び直す」。zustand はその「購読」の部分を React 用に用意したライブラリ。

store の形

export const useAppStore = create<AppState>((set, get) => ({
  project: actions.createProject(DEFAULT_PRESET),
  images: {},
  videos: {},
  ui: { selectedItemId: null, playheadFrame: 0, isPlaying: false, importing: false, exporting: false },

  setItemDuration: (itemId, frames) => { ... },
  select: (itemId) => set((s) => ({ ui: { ...s.ui, selectedItemId: itemId } })),
  ...
}))
  • AppState の型（ファイル冒頭）に、データ と 操作（action） の両方が並んでいる。Python のクラスで言えば属性とメソッドだが、クラスは使わない。
  • create に渡した関数が初期状態を返す。set は状態を差し替える関数、get は今の状態を読む関数。
  • action の中で set({ project }) や set((s) => ({ ui: { ...s.ui, selectedItemId } })) と呼ぶ。渡したフィールドだけが差し替わる（浅い merge）。ui の中の 1 つを変えるときは、4 章のスプレッドで ui を作り直す。

action は純粋関数に任せる

store.ts の冒頭コメント:

プロジェクトの変更は projectActions の純粋関数に任せ、ここでは画像の所有と UI 状態だけを扱う。

projectActions.ts の関数は (project, ...) => project の形で、store も React も知らない。だから projectActions.test.ts は vitest だけで動き、ブラウザが要らない。テストを読むと「追加した素材は 5 秒」「上限を超えたら追加しない」「同じ値なら元のまま（toBe(p)）」といった仕様がそのまま書いてある。

store 側に残っているのは、

  • 画像や動画の 所有（ImageBitmap を閉じる、使い終わった動画を解放する）。これは副作用なので純粋関数に入れない。
  • ui（選択中、再生中、取り込み中、書き出し中）。

部品からの読み方: セレクタ

const items = useAppStore((s) => s.project.items)
const exporting = useAppStore((s) => s.ui.exporting)
const setItemDuration = useAppStore((s) => s.setItemDuration)

useAppStore(セレクタ) は「状態のこの部分」を返し、その部分が変わったときだけ 部品を描き直す。useAppStore() と引数なしで全体を取ると、何が変わっても描き直されて遅くなるので、必ず必要な部分だけ取る。action も同じ書き方で取る。

追ってみる: 尺のスライダー

  1. MediaList.tsx: <FrameSlider ... onChange={(frames) => setItemDuration(item.itemId, frames)} />
  2. FrameSlider.tsx: スライダーを動かすと onChange(Number(e.target.value))。矢印なら onChange(stepFrames(...))。
  3. store.ts: setItemDuration: (itemId, frames) => set((s) => withProject(s, actions.setItemDuration(s.project, itemId, frames)))。withProject はファイルの下にある補助関数で、新しい project が元と同じオブジェクトならそのまま返し、違えば再生位置（ui.playheadFrame）も新しい尺の範囲に収めて返す。
  4. projectActions.ts の setItemDuration: clampDuration で整え、同じ値なら元の project を返す。違えば items を map で作り直し、clampAfterResize（つなぎとテロップを尺に収める）、clampTrims（動画の開始位置を収める）を通す。
  5. set で差し替わる。s.project.items を見ている MediaList、TotalDuration、PreviewCanvas が描き直される。s.ui.exporting だけを見ている部品は、その値が変わらない限り動かない。

テスト projectActions.test.ts の「変えたあとはトランジションとキャプションが切り詰められる」が、4 の仕様をそのまま書いている。

「同じなら元を返す」の意味

expect(setItemDuration(p, 'p1', 150)).toBe(p)
expect(removeItem(p, 'nope')).toBe(p)

変化が無いときは 同じオブジェクト を返す。store はそれを見て set を呼ばず、部品は描き直されない。4 章の「壊さずに変える」の裏返しで、「変えないときは新しく作らない」。Python で if new == old: return old と書くのと同じだが、ここでは == ではなく同一性で判定するので速い。
