# 2026-10-14 M3(B2) 動画の取り込み UI・トリム UI・プレビューの <video>、の二重レビュー

対象: `main..m3-video`（`MediaPicker`、`media/videoPoster.ts`、`TrimEditor`、`preview/previewVideos.ts`、`usePreview` の動画対応、
`importVideo` をメモリ上の Blob に）。約 410 行。

## Codex（3 件）
- [P1] 元動画が見える長さより短いとき、停止中に末尾を超えた時刻を要求すると、ブラウザが末尾に戻す → `seeked` → 描き直し → 再要求、の循環になる。
  再生中も末尾で `play()` を呼び直して先頭に戻る（仕様に沿ったフェイクで再現）。
- [P2] シーク中（`seeking`）でも `readyState >= 2` なら `<video>` を返すので、トリム変更やスクラブで前のフレームが描かれ得る。
- [P2] 書き出し中もプレビューのスライダーとトリムが動き、`<video>` のシーク（デコード）が書き出しのデコーダと並行して走る。

## Claude `/code-review main..HEAD high`（10 件）
1. 末尾や フレーム境界に寄せられると永久に再シークする（Codex P1 と同じ）。
2. `ended` のあとの `play()` が先頭に戻る（Codex P1 と同じ）。
3. プレビューの時刻に `firstTimestampSec` を足していないので、先頭時刻が 0 でない動画で書き出しとずれる。
4. `new Blob([await file.arrayBuffer()])` は読み込みの瞬間にファイルの 2 倍のメモリを使う。
5. 次に見える動画を事前にシークしていないので、切り替わりの数フレームでポスターが出る。
6. `TrimEditor` の「△秒まで」が、元動画が短いとき元動画の尺を超える。
7. 上限超えの案内が取り込みの完了まで表示されない。
8. `sourceDurationFrames` が `durationSec × fps` で、先頭時刻の分だけ実体より多い（トリム上限が実体より大きい）。
9. `compileTimeline` が `ItemEditor` / `usePreview` / `clampTrims` の 3 か所で走る。
10. `isVideoFile`（純粋関数）にテストがない。`PreviewVideos` が DOM を直接触り、シークと再生の状態機械が未検証。

## 人間の判断
- Codex P1 / Claude 1, 2, 10: 採用。判断を純粋関数 `preview/videoPlan.ts` の `planFrame` に切り出し、テストを先に書いた
  （要求済みの時刻は再要求しない、末尾を過ぎた時刻は末尾に留める、`ended` 中は `play()` しない、読み込み前は制限しない）。
  `PreviewVideos` は状態を読んで `planFrame` の結果を適用するだけにした。`isVideoFile` は `media/fileTypes.ts` に移してテスト。
- Codex P2（シーク中は null）: **不採用**。ポスターに切り替えるとスクラブ中にちらつく。`seeked` で描き直されるので数十 ms で正しくなり、
  plan §3.3 の「数フレーム差は許容」の範囲。コメントに理由を残した。
- Codex P2（書き出し中）: 採用。`usePreview` が `ui.exporting` を見て `<video>` を止めてポスターで描き、シークとトリムのスライダーを無効にする。
- Claude 3: **不採用（指摘が逆）**。`<video>` の `currentTime` は先頭フレームを 0 とするので、プレビューは足さないのが正しい。
  書き出し（mediabunny のタイムスタンプ）だけ `firstTimestampSec` を足す。足すと逆にずれる。
- Claude 4: 採用。`new Response(file).blob()` で中身を直接 Blob に読む（ADR 012 の補足を修正）。
- Claude 5: 採用。描画のあと、次に見える素材が動画なら開始位置へ先にシークしておく（`frameAt` を停止扱いで呼ぶ）。
- Claude 6, 7, 8: 採用。
- Claude 9: 不採用。compile は安価で、3 か所とも「items からその場で計算する」のが一番読みやすい。引数が増えたら見直す。

## 2 者の比較
- 両方が指摘: 末尾のホールドの循環（Codex は仕様に沿ったフェイクで 9 回目のシークを再現、Claude は iOS のフレーム境界への寄せも挙げた）。
- Codex だけ: シーク中の描画、書き出し中の競合。
- Claude だけ: メモリのピーク、事前シーク、表示と尺の補正、テストの欠落。
- Claude 3 は誤り。`<video>` と mediabunny で時刻の原点が違うことを、レビュアーも実装者も明示的に確認する必要がある（記録として残す）。

## 修正後の確認
- lint / typecheck / 213 件のテスト通過。
- ヘッドレス Chrome: 1 秒ごとに色が変わる動画で、開始位置 3 秒のプレビュー（停止・再生・2 番目の素材）と書き出しの色が一致。
  2 秒（65 フレーム）の動画を 10 秒の素材にして、停止中も再生中も末尾の色（青）で止まり、先頭に戻らない。
  回転メタデータ付きの H.264（MOV）はプレビューと書き出しで同じ向き（上が青、下が赤）。HEVC はヘッドレス Chrome がデコードできず、取り込み時に案内が出る。
- 未確認: iPhone / Android の実機（`<video>` の preload、自動再生、同時 `<video>` 数、HEVC、HDR）。M3(C) で確認する。

## 学び（教科書向けメモ）
- 「ブラウザの状態を読んで操作を決める」コードは、判断（純粋関数）と操作（DOM）に分けると、循環や巻き戻りのような
  状態機械の不具合をテストで固定できる。
- 同じ「時刻」でも原点が違うことがある（`<video>` は先頭フレーム = 0、コンテナのタイムスタンプは 0 とは限らない）。
  レビューの指摘が正しいとは限らないので、仕様を確認して記録する。
- 「シーク中はどう描くか」のような UX の判断は、指摘を理由つきで不採用にしてよい。
