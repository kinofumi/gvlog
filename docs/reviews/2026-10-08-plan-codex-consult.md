## Codex の指摘（原文）

埋め込まれたプランを対象に、実装を阻む問題から順に確認します。ブラウザ・コーデックの対応状況は公式資料で照合し、指定された禁止ディレクトリは読みません。
主な問題は、対応端末の保証が能力判定だけに依存している点と、トランジション前後の動画時刻が未定義な点です。公式資料の検索は接続タイムアウトで確認できていないため、対応状況の断定と設計上確定できる問題を分けて指摘します。
**最優先は、M0 を「能力一覧の表示」から「実素材で無音 MP4 を完成させる検証」に変えることです。現状は最大の成立リスクを M3 まで先送りしています。**

公式資料の検索は接続タイムアウトで確認できていません。以下、ブラウザ対応の記述は未検証として扱い、設計上の問題を優先します。

1. **【致命的／§技術調査・M0〜M3】API 対応とアプリの成立を同一視している。**  
   音声を省いても、HEVC の入力、H.264 の出力、回転、HDR、実機メモリは残ります。`canEncodeVideo()`／`canDecode()` の成功は、実ファイルを最後まで処理できる保証ではありません。  
   **修正:** M0 で iPhone の縦 HEVC 動画と写真を読み込み、1080p・10 秒・無音 MP4 を生成し、写真アプリと CapCut に取り込むところまで通す。最低対応 OS と推奨 OS の実機を分け、成功した条件だけを対応表に載せる。mediabunny の採用確定もその後。

2. **【致命的／§2】オーバーラップ区間の「素材内時刻」が未定義。**  
   後続動画はコア開始より `d/2` 早く見えます。visible 開始を `sourceStart` にすると、コア開始時には既に `d/2` 秒進みます。コア開始を `sourceStart` にすると、トリム位置より前の素材が必要です。現状は前者らしいものの、仕様になっていません。  
   **修正:** `sourceTime = trimStart + (t − visibleStart)` などを明文化し、必要素材尺を `visibleEnd − visibleStart` とする。トランジション変更で動画の見える時刻が変わることも定義する。Ken Burns、キャプション、先頭・末尾、最後の `transitionOut` も同じ時間規則で決める。

3. **【重大／§2】尺の不変条件を満たせない入力がある。**  
   10 秒に 11 素材は最小 1 秒と両立しません。3 等分は 0.1 秒刻みで厳密に等分できず、24fps では 0.1 秒が整数フレームになりません。1 素材だけの尺変更、空プロジェクト、再配分先が全て最小尺の場合も未定義です。  
   **修正:** 内部時間を整数フレームに統一し、総フレーム数・端数配分・追加上限・変更可能範囲を定義する。尺を短くした際のトランジションとキャプションの再検証も必須。

4. **【重大／§3〜4】同期描画 API と非同期デコードの接続が欠けている。**  
   `getFrame()` は同期なのに、デコードは非同期です。必要フレームを待つ処理がなく、`null` が黒フレームとして出力される危険があります。`timestamp + duration > t` だけでは、そのフレームが `t` より未来でないことも確認できません。  
   **修正:** 各出力フレームで `await prepareFrames(t)` → 同期描画 → encode → 不要資源の解放、という順序を明示する。VFR、非ゼロ開始時刻、シーク、EOF、デコード失敗を扱い、フレームの所有者と `close()` 担当を固定する。

5. **【重大／§4・9】メモリ対策が出力サイズ中心になっている。**  
   出力が約 10MB でも、4K 入力のデコード面、48MP 写真の一時展開、GPU 資源、ImageBitmap、エンコーダ内部バッファは別です。縮小指定が元画像の全面展開を回避する保証もありません。「タブ 1〜1.5GB」は安全予算として使えません。  
   **修正:** 写真の保持枚数、入力画素数・容量、出力フレーム数に上限を設ける。画像も必要な分だけ展開する。失敗・キャンセル時の一括解放を設計し、低メモリ端末で連続書き出しを検証する。720p への変更は固定プリセットと衝突するので、黙って下げず仕様を決める。

6. **【重大／§4・6】出力契約とフォールバックが矛盾している。**  
   MP4 素材を揃えるアプリで WebM を出すと、仕上げ担当への納品要件を満たせません。また、1080p60 を許可しながら H.264 Level 4.0 固定では成立しない組み合わせがあります。URL から極端な尺・fps・解像度も入り得ます。  
   **修正:** v1 は H.264／MP4、30fps、許可した解像度と尺だけに限定する。能力判定は実際の幅・高さ・fps・ビットレートで行う。リンクも保存データも同じスキーマで検証し、MP4 非対応は非対応として止める。

7. **【重大／§5】「タブが落ちても再開可能」を保証できる保存設計ではない。**  
   Blob、JSON、一覧の個別保存に加え、JSON は遅延保存です。削除直後に Blob を GC して落ちると、保存済み JSON が存在しない Blob を参照します。容量不足、書き込み失敗、保存中の再編集、複数タブも未処理です。  
   **修正:** メタデータ更新をトランザクションでまとめ、GC は参照削除のコミット後に行う。「保存中／保存済み／失敗」を表示し、保証は「保存済み状態から復元」に限定する。永続ストレージ要求や当日書き出し案内は、保存成功の保証にはなりません。

8. **【重大／§3・9】向き・色・合成の仕様を実装後の確認に逃がしている。**  
   回転をライブラリとアプリで二重適用する余地があります。HDR の色崩れを README だけで扱うと、既存の iPhone 動画を救えません。crossfade も、前後両方へ単純に減衰 alpha を掛けると合成方法によって暗くなります。  
   **修正:** M0 で回転と HDR を含む実素材を検証する。HDR は対応処理か取り込み拒否を決める。crossfade は具体的な合成式を定義し、同じ色同士を混ぜても輝度が変わらないテストを置く。キャプションを映像と一緒に消すのか、合成後に別描画するのかも固定する。

9. **【重大／§検証方法・4】実機検証と保存操作に必要な条件が抜けている。**  
   LAN の `http://<PCのIP>` は通常 secure context にならず、WebCodecs や共有機能の検証手順として不足しています。共有はユーザー操作が必要で、書き出し完了後の自動呼び出しを前提にできません。写真保存先の表示もアプリ側では保証できません。  
   **修正:** HTTPS の検証環境を M0 に用意する。生成後に独立した共有ボタンを押す設計にし、共有のキャンセルと失敗を分ける。画面ロック・バックグラウンド移行時の中断処理、キャンセル不能になった main thread の扱いも定義する。

10. **【重大／§11】モック中心のテストで主要リスクが抜ける。**  
    `@napi-rs/canvas` は Safari のフォント描画・色管理・Canvas 動作の証明にはなりません。一方、IndexedDB の整合性や障害時処理まで「実機で補う」に寄せすぎです。`ffprobe` の属性確認だけでは、途中の黒フレームや間違った素材も見逃します。  
    **修正:** TDD は尺・区間・状態遷移に集中する。ブラウザ結合テストで保存失敗、キャンセル、実際の短い動画の書き出しを確認する。出力は属性に加え、冒頭・境界・末尾のフレーム内容も検証する。対応を約束する iPhone は手動実機試験を必須にする。

11. **【中／§1・8・13】教材としての最小構成が、実装計画に反映されていない。**  
    Worker 優先と main thread から開始、6 種トランジションと 2 種から開始、スライス構成とフラットストアが併存しています。プレビューと export も別の動画再生系で、同期バグを二重に抱えます。  
    **修正:** v1 を main thread、H.264、30fps、1 フォント、cut、基本テロップに絞る。動画の成立検証だけは先に済ませ、crossfade・Worker・追加デザインを後章へ移す。予告した全モジュールを最初から作らない。シークや尺調整の使いやすさは M5 まで延期しない。

12. **【中／§14】レビュー回数は多いのに、承認対象が曖昧。**  
    「全 PR 必須」と「UI は省略可」が矛盾しています。修正後の再レビュー、対象コミット、未解決の重大指摘、ツールが使えない場合の扱いがありません。小変更にも複数レビューと原文記録を課すと、教材作成より儀式が重くなります。  
    **修正:** 全 PR は lint・型検査・必要なテスト、重要変更だけ独立 AI レビューを必須にする。記録は対象 SHA、重要指摘、判断、修正後の検証結果を中心にする。最終変更後の差分を確認し、未解決の重大問題と必須実機試験の未実施をマージ阻止条件にする。初回は比較先ブランチがないため、全ファイルレビューの手順も別途必要です。
