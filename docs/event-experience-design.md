# 「イベント体験の設計」事業の構想メモ

> 作成日: 2026-11-16。gvlog を作ってみて見えてきた、次の事業の考え方をまとめたもの。
> 判断の記録であって仕様ではない。試行を重ねて書き直す。公開リポジトリなので、相手先の名前や金額は書かない。

## 一言で

スマホ向けの「その催しのためだけの Web アプリ」を、イベント体験の一部として設計して提供する。
売るのは「使い捨てアプリ」ではなく **イベント体験の設計** で、アプリはその成果物の 1 つ。

## 背景: gvlog で分かったこと

- サーバーなし、ログインなし、アプリストアなし、無料の配信（GitHub Pages）で、約 5 週間で本番に出せるものが作れた。
- データが端末の外に出ないので、個人情報の扱いが軽い。自治体、学校、医療系の催しでは強い売り文句になる。
- 参加者は URL を開くだけ（ホーム画面に追加もできる）。終わったら何も残らない。「使い捨て」は作る側の都合ではなく、参加者と主催者にとっての利点として語れる。
- 作る時間より、実機確認と当日の支えに要る時間の方が大きかった（HEVC の動画、ホーム画面からの開き方、共有シート、Android のインストール。`docs/testing-checklist.md`、ADR 022、023）。
- AI と一緒に作ったので、コードを書く速さは差にならない。差になるのは企画と画面の設計、端末ごとの落とし穴の知見、二重レビューとチェックリストの手順、そして「教科書」として説明できる進め方。

## 何を売るか、何を売らないか

| 売るもの                                                           | 売らないもの                               |
| ------------------------------------------------------------------ | ------------------------------------------ |
| 催しの流れ（集合 → 体験 → 共有 → 発表）に合わせた画面と体験の設計  | 「アプリを作ります」だけの受託             |
| 当日に動く Web アプリ（URL と QR コード）                          | アプリストアに出す native アプリ           |
| 実機での確認結果（対応表、チェックリスト）                         | サーバーや会員登録を伴う仕組み             |
| 当日の支え（立ち会い、案内の紙、困ったときの連絡先）               | 恒久的な運用・保守（終わったら止める前提） |
| 終わったあとの振り返り（何人が最後まで行けたか、どこで詰まったか） | 参加者のデータの収集・分析                 |

## 型は残し、中身は使い捨てる

gvlog を部品に分けて、催しごとに差し替えるのは中身だけにする。

| 部品                   | gvlog での場所                                | 催しごとに変えるもの           |
| ---------------------- | --------------------------------------------- | ------------------------------ |
| 栞（流れ・地図・会場） | `src/guide/nakaminato.ts`、`EventGuide.tsx`   | 日時、場所、流れ、注意書き     |
| おすすめ（見どころ）   | `src/guide/tips.ts`、`TipsGuide.tsx`          | 場所と撮り方のメモ             |
| 撮影と編集             | `src/timeline/`、`src/render/`、`src/export/` | 上限の尺、縦横比（プリセット） |
| つなげる               | `src/join/`                                   | 表紙の文字、BGM                |
| 表紙とアイコン         | `Splash.tsx`、`public/icon-*.png`、manifest   | 絵と名前                       |
| BGM                    | `public/bgm/`、`scripts/make-bgm.sh`          | 曲（権利の確認込み）           |

2 件目からの原価が下がり、価格に「型の流用」と「作り込み」の 2 段を作れる。
部品化の作業は gvlog の次の章としてやる（イベント後。ADR を書く）。教科書にもそのまま載る。

## 品質と当日の支え

「使い捨て」でも、当日に動かなければやり直しがきかない。品質の要求は本番そのもの。

- 実機確認を見積もりの独立した項目にする。チェックリストと対応表をそのまま納品物にする。
- 当日の支えを別の項目にする（立ち会い、紙の案内、連絡先）。
- 動かない端末があったときの逃げ道を先に決めておく（紙、別の人のスマホ、主催者の端末）。
- 二重レビュー（Claude → Codex → 人）と devlog は続ける。手順そのものが信頼の根拠になる。

## 権利と安全

案件ごとに同じ判断が要るので、ひな形を作る。

- 撮られる人の肖像: 当日の案内に「撮ってよい・よくない」の約束を入れる。
- 音楽: 自作か、商用利用と再配布が許される出どころ（gvlog は Suno の有料プランと credit 表示。ADR 019）。
- 利用規約と連絡先: アプリの中か案内の紙に 1 か所。
- データ: 端末から出ない設計を保つ。出す必要が出たら、それはこの事業の型ではない別案件として扱う。

## 気になる点

- **単価と継続性。** 催しの予算は小さく、1 回きりでは次の売上が自動では立たない。型の流用と、研修・講座（下記）で補う。
- **期待の食い違い。** 「使い捨て」と聞くと安く・雑に、と受け取られる。言葉を「その催しのためだけの」に変える。
- **端末の多様さ。** iPhone と Android で挙動が違う所が必ず出る。対応表に「確認できたものだけ載せる」を守る。
- **作ること自体の価値の低下。** AI で誰でも作れる。設計と手順と知見で差をつける。

## 価格の考え方（金額は書かない）

1. **型の流用**: 既存の部品の中身を差し替える。短納期、低価格。
2. **作り込み**: 新しい画面や体験を設計する。企画の打ち合わせから。
3. **当日の支え**: 1、2 のどちらにも足せる項目。
4. **振り返り**: 終わったあとの数字と所見。次回の提案につなげる。

別の商品として、**「AI との開発の進め方」の研修・講座**。gvlog の教科書化（`docs/study/`、ADR、devlog、レビュー記録）がそのまま教材になる。協会の役割とも合う。

## 検証の計画

1. **2026-11-28 を事例にする。** 記録する数字:
   - 手助けなしで書き出し（保存）まで行けた人の割合
   - つまずいた画面と、その回数
   - 問い合わせの数と内容
   - 端末の内訳（iPhone / Android、OS の版）と動かなかった組み合わせ
2. **1 枚の提案書を書く。** できること、できないこと、価格の段、当日の支え、権利の扱い。
3. **分野の違う催しで 2〜3 件、有償の試行。** 同じ型で中身だけ違うものが向く（観光の街歩き、社内研修、学校行事）。
4. **3 件やってから判断する。** 続けるか、型を変えるか、やめるか。判断の材料は 1 の数字と、1 件あたりにかかった時間の内訳（設計、実装、実機確認、当日）。
